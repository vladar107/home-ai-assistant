# 0157 — Pi 1.1.0 in production

Status: `in-progress`

## Context

The image pins the Pi coding agent at 1.0.0 (`third_party/pi-runtime`, the Dockerfile's
`pi --version` check, and `config.DefaultPiVersion`, which the Pi runtime's version check and the
eval harness of plan 0155 compare against). The version the runtime expects is also set by
`HOME_AGENT_PI_VERSION`: the Compose file defaults it to 1.0.0 and the example env files set it,
so a 1.1.0 image with those values left alone fails the version check on every turn. The pin
has not moved since it was introduced. The operator's local development server already runs
Pi 1.1.0, so what is tested locally is not what production runs, and the eval harness, which
insists on the pinned version, refuses the local Pi.

The application depends on Pi's behaviour in specific ways: the RPC event stream and its order
(the runtime's event handling and the Pi stand-in in `internal/testutil/pifixture`, whose
comments describe Pi 1.0.0's order for parallel tool batches and retries), the session file
format (resumed conversations, image stripping in `internal/runtime/pi/transcripts.go`), the
locking of `auth.json` during refresh (`internal/turn/engine.go`), the per-turn bridge extension,
and the vendored web search extension.

Pi's changelog from 1.0.1 to 1.1.0 lists no change to the RPC protocol, the session format or
the extension API that the bridge uses. The changes that touch this application:

- Provider errors "Selected model is at capacity" (1.0.1) and `server_busy` (1.1.0) are retried
  instead of ending the turn.
- A Sign in with ChatGPT refresh that was cancelled mid-request no longer invalidates the refresh
  token (1.0.3). The application cancels turns, so this removes a way to be logged out.
- Pi's built-in MCP support gained `--no-mcp` (1.0.4), and `--tools` now keeps MCP tools unless
  an entry names them. MCP is already off for this runtime: it passes `--no-extensions`, which
  leaves out every built-in extension, MCP included, and `--no-approve`, which ignores
  trust-gated project files; the runtime uses `--no-tools` or `--no-builtin-tools`, never
  `--tools`.
- `agent_settled` carries `aborted` (1.1.0), an added field.
- Pi no longer ships an `npm-shrinkwrap.json` (1.0.2), so its transitive dependencies are pinned
  only by this repository's lockfile. Against the current lockfile, two third-party packages
  change: `@anthropic-ai/sdk` 0.124.0 to 0.129.0, and `brace-expansion` 5.0.9 to 5.0.12, now a
  direct dependency; the packages with install scripts are the same ones, and the build already
  passes `--ignore-scripts`.
- Pi 1.1.0's authentication storage, session manager and RPC mode are byte-identical to 1.0.0's;
  the agent loop adds `durationMs`, and the extension API only gains additions.

## Goal

Production, the local development server and the eval harness run the same Pi, 1.1.0, with every
assumption the application makes about Pi checked against that version, and no MCP server
reachable from a turn through Pi's own MCP support whatever configuration it finds.

## Decisions

- **Move the pin to 1.1.0 in one change.** `package.json`, the regenerated `package-lock.json`
  (in the runtime base image, as `third_party/pi-runtime/README.md` describes), the Dockerfile's
  version check, `config.DefaultPiVersion`, the Compose default of `HOME_AGENT_PI_VERSION`, and
  the example env files change together, so the version check, the image and the eval agree.
  The ignored local env files (the development `.env` and the NAS env file) are updated in the
  same step, before the image is deployed.
- **Say `--no-mcp` as well, as defence in depth.** MCP is already off through `--no-extensions`;
  the explicit flag keeps it off if a later Pi changes what that switch covers. A runtime test
  asserts the flag. Pi 1.0.0 rejects the flag, so the flag and the 1.1.0 pin ship and roll back
  together: rolling back means reverting this change, not only the image.
- **Name busy and capacity retries.** The runtime's retry categories gain one for "server busy"
  and "at capacity" errors, so the retries Pi 1.1.0 now makes show in telemetry by their cause
  instead of as `other`.
- **Check every 1.0.0 assumption against 1.1.0, not by the changelog alone.** Each comment or
  fixture behaviour that names Pi 1.0.0 is verified against Pi 1.1.0's source in the installed
  package (or a recorded run where the source is not decisive), and updated to name 1.1.0 only
  once it holds. A behaviour that changed is fixed in the runtime and mirrored in the fixture.
- **Review the lockfile diff.** Every new or changed transitive package is listed in the commit
  message body by name and version; a new package with an install script, native code or a
  network download at runtime is a stop-and-ask.

## Approach

1. **Bump and lock** (Simple). Update `package.json` to 1.1.0, regenerate `package-lock.json` in
   `node:24.19.0-alpine3.24` with `--package-lock-only --omit=dev --ignore-scripts`, confirm the
   lockfile diff holds only the packages listed above, update the README's version, integrity
   and the shrinkwrap sentence (pinning now rests on this lockfile), the Dockerfile check,
   `config.DefaultPiVersion`, the Compose default, `.env.example` (value and comment),
   `deploy/nas.env.example`, the tests that name the version, and the ignored local env files.
   Ignore `third_party/pi-runtime/node_modules` in `.gitignore`.
2. **Verify the assumptions** (Complex). Read Pi 1.1.0's code for each place that names Pi 1.0.0
   behaviour: `internal/testutil/pifixture/fixture.go` (argument reading, the parallel tool batch
   order, retry scheduling, session file writing), `internal/runtime/pi/transcripts_test.go`
   (the session file with a photo), and `internal/turn/engine.go` (the `auth.json` lock). Update
   each comment to name 1.1.0 once its claim holds; fix the runtime and the fixture where one
   does not.
3. **`--no-mcp` and the retry category** (Simple). Add the flag to the runtime's arguments and the
   busy and capacity category to its retry categories, each with a test.
4. **Real RPC smoke run** (Simple). Start the installed Pi 1.1.0 with the runtime's exact
   argument list in RPC mode, from a test-only path or a one-off command, with no model call:
   it must accept every flag and load the bridge and the web search extension. The Pi fixture
   accepts any argument, so the Go suite cannot show this.
5. **Build and deploy** (operator). Build the image, confirm `pi --version` prints 1.1.0, deploy
   tag-pinned as usual, record the digest.

## Validation

- Formatting, module tidiness, vet, build, the full test suite with and without the race detector,
  and `scripts/check-plans`.
- No reference to the 1.0.0 pin remains outside lockfiles and `node_modules` (a search for
  `1.0.0` next to Pi in code, deploy files, env examples and docs).
- The real RPC smoke run of step 4 passes.
- The image builds and its `pi --version` check passes.
- By the operator after deployment: a chat turn with a tool call, a web search, a resumed
  conversation with a photo, a cancelled turn, a scheduled run, and `/status` usage; the eval
  harness's `run` accepts the local Pi without an override.

## Risks and open questions

- **Retried provider errors lengthen some turns, and a long retry delay reads as a stall.** Pi
  retries up to three times with a base delay of 2 seconds, and honours a provider-supplied delay
  up to 60 seconds. The runtime's stall timer is 45 seconds and resets on every event, including
  the retry's start; a provider delay between 45 and 60 seconds is silence beyond it, so the
  runtime stops Pi and, when nothing was streamed yet, reruns the turn once, reported as a stall.
  The turn timeout still bounds the whole. Recommendation: accept this for now and watch the new
  retry category; lower Pi's maximum retry delay below the stall timeout only if such stalls show
  up.
- **Changelog completeness.** The changelog may omit a behaviour the application relies on; step 2
  exists for that reason, and the post-deploy checks cover the paths a silent change would break.
- **Later upgrades.** Nothing here automates future bumps; the README's refresh steps stay the
  procedure.
